# NS-409 Frontend and Codex Recovery Plan

Status: replanned, in progress, visually rejected
Updated: 2026-06-23

## Current Decision

`NS-409` is no longer a single "frontend polish" task. It is now the recovery plan for the current frontend, with Codex as the first-class product risk.

The previous milestone order must not be followed mechanically. M2 and M3 features that were already implemented may still need contract, API, storage, and UI changes if the rebuilt frontend exposes gaps.

## Why This Replan Exists

- The current React UI builds, but user visual/product acceptance failed.
- Codex was heavily changed in the frontend and is now only a shell.
- The old Codex backend has more capability than the current frontend wrapper exposes, but that does not prove the API is sufficient for the new UI.
- Write hierarchy behavior is not acceptable, and the product hierarchy expectation must be rechecked instead of patched superficially.
- Settings, Review, and Workshop are not finished product workflows.

## Current Codex Reality

Backend routes currently exist for:

- categories: list/create/update/archive/restore;
- entries: list/create/get/update/archive/restore;
- mentions by entry and by scene;
- relations: list/create/update/archive/restore;
- progressions: list/create/get/update/archive/restore;
- character knowledge: list/create/get/update/archive/restore;
- effective state by scene/entry/viewer;
- Codex context preview by scene and pinned IDs;
- Codex search.

Current frontend Codex wrapper exposes only:

- list categories;
- list entries;
- create entry;
- get entry.

Current frontend Codex workspace:

- loads categories and entries;
- filters locally;
- creates a default entry;
- opens/collapses a detail panel;
- renders read-only details/research/mention/tracking placeholders;
- does not edit and save entries;
- does not load relations, progressions, knowledge, mentions, effective state, context preview, or search from the UI workflow.

Therefore the next step is not "draw a nicer Codex page". The next step is a Codex contract and workflow audit followed by implementation.

## Reopened Foundation Questions

These questions must be answered by implementation, not assumed away:

- Is `Book -> Act -> Chapter -> Scene` still the storage contract, with `Volume -> Chapter -> Act -> Scene` only as UI terminology, or must the M2/M3 hierarchy contract change?
- Does Codex need category-specific detail schemas instead of the current free-form `details: Record<string, string>`?
- Does the entry index need a lightweight summary/list projection instead of returning full documents for dense UI?
- Does the detail workspace need lazy tab payloads or a single aggregate endpoint?
- Are current relation/progression/knowledge routes ergonomic enough for a tabbed author-facing editor, or do they need view-model endpoints?
- How should ambiguity resolution be represented? Current mention indexes record ambiguity, but there is no author-facing disambiguation workflow.
- Does Codex need real delete/trash behavior, or is archive/restore the correct product model?
- What scene/evidence picker APIs are needed so users can create progressions and knowledge without pasting IDs?
- How should Codex context preview relate to the newer M4 `ContextBundle` preview so there are not two incompatible context concepts?

## Work Packages

### NS-409.0 Rebaseline and Guardrails

Goal: make the current truth unambiguous before more UI code changes.

Tasks:

- Keep `docs/design/**/backups/` protected.
- Do not use old `NS-409A` through `NS-409F` images as current implementation guidance.
- Keep all active state in `STATUS.md`, `HANDOFF.md`, `TASKS.md`, `CHANGELOG.md`, this file, and `docs/testing/NS-409_ACCEPTANCE.md`.
- Confirm current app routes, API wrappers, server routes, contracts, and storage methods before each major Codex change.
- Keep user-facing copy isolated for later bilingual adaptation.

Acceptance:

- The task index and handoff describe the new plan.
- No new routine status files are created.

### NS-409.1 Foundation Audit: Hierarchy, Project Creation, and Codex API

Goal: audit whether M2/M3 foundations still match the rebuilt frontend.

Tasks:

- Audit project creation from an empty library, including disabled states and command availability.
- Audit Write hierarchy data and UI terminology:
  - current storage model;
  - current API inputs;
  - current UI labels;
  - required user model: `Volume -> Chapter -> Act -> Scene`.
- Decide whether hierarchy changes are UI terminology only, API projection changes, or storage/migration changes.
- Audit Codex contracts, routes, storage methods, and frontend wrappers against the new tabbed/detail workspace.
- Produce a precise API gap list before adding UI-only workarounds.
- Identify which storage logic should move out of `packages/storage/src/index.ts` before new Codex behavior grows it further.

Acceptance:

- The gap list is recorded in this file or `docs/testing/NS-409_ACCEPTANCE.md`.
- Any contract/storage change required by the new UI is explicitly named before implementation.

### NS-409.2 Project and Library Recovery

Goal: make the app usable from a zero-project state.

Tasks:

- New Project must be usable when the library is empty.
- Project creation must not depend on developer/API intervention.
- Empty states must allow primary actions instead of blocking all pointer interaction.
- Project creation must create a coherent first `Volume`, `Chapter`, `Act`, and `Scene` according to the resolved hierarchy decision.
- The left sidebar must reflect empty, loading, and active project states without misleading counts.

Acceptance:

- A user can start from no projects and create/open a project through the UI.
- No-project state has no disabled primary dead end.
- Tests cover empty-library creation.

### NS-409.3 Write Hierarchy Recovery

Goal: repair the writing hierarchy as a product interaction, not a cosmetic patch.

Tasks:

- Implement the resolved hierarchy model consistently in labels, data projection, add actions, delete actions, selection, and breadcrumb.
- Add must be one compact menu near the hierarchy title, similar to a contextual menu.
- New items receive default names.
- Rename is available after creation, including double-click rename where appropriate.
- Delete sits near Add and deletes only the selected hierarchy item after confirmation.
- Collapse behavior keeps content anchored naturally; it must not auto-center large empty cards.
- Scroll exists wherever hierarchy content can overflow.
- Scene save/select behavior must remain stable after hierarchy edits.

Acceptance:

- Add, rename, delete, collapse, scroll, and scene selection work for every hierarchy level.
- Tests cover at least create/rename/delete for the selected hierarchy target.
- No regression to the old "three large permanent add buttons" design.

### NS-409.4 Codex API and Frontend Wrapper Expansion

Goal: expose existing backend capability to the frontend and identify truly missing APIs.

Tasks:

- Extend `apps/web/src/api/codex.ts` for all existing Codex routes needed by the UI:
  - update/archive/restore entries;
  - relations;
  - progressions;
  - knowledge;
  - entry mentions;
  - scene mentions;
  - effective state;
  - Codex context preview;
  - search.
- Add typed request/response coverage from `packages/contracts/src/codex.ts`.
- Decide whether list views need summary endpoints instead of full documents.
- Decide whether tabbed detail needs aggregate view-model endpoints.
- Decide whether category-specific fields require contract changes.
- Do not add frontend mock state to hide missing API capability.

Acceptance:

- Frontend Codex API wrapper covers the routes the product UI uses.
- Missing API needs are documented as contract tasks, not hidden in component state.
- Unit tests or integration tests cover critical wrapper behavior.

### NS-409.5 Codex Entry Workspace

Goal: make Codex a real author-facing entry editor.

Tasks:

- Entry index supports dense scanning without wasting the page.
- Selecting the same entry hides details.
- Detail workspace uses tabs/sections for:
  - Details / canon description;
  - Research;
  - Relations;
  - Mentions;
  - Tracking / context policy;
  - Progressions;
  - Character knowledge;
  - Effective state.
- Details and research can be edited and saved with revision protection.
- Aliases, tags, mention rules, context policy, and category are editable where product-safe.
- Relations can be listed, created, updated, archived, and restored.
- Progressions and character knowledge can be listed and inspected at minimum; create/edit is required if the API audit confirms necessary scene/evidence picker support.
- Mentions and ambiguities must be visible without pretending ambiguity is resolved.
- Archive/restore is available; hard delete requires a separate product decision.

Acceptance:

- A user can create an entry, rename it, edit details, edit research, save, reload, and see persisted data.
- Relation and mention tabs use real APIs.
- Progression/knowledge/effective-state tabs honestly show real data or a scoped unavailable state.
- Revision conflict behavior is visible and recoverable.

### NS-409.6 Codex Integration With Write, Plan, and AI Context

Goal: make Codex useful in writing, not isolated in its own page.

Tasks:

- Write page Codex-in-scene data uses real scene mention/context APIs.
- Plan/tracking views display Codex names and status using stable IDs.
- Context preview aligns old Codex context preview with M4 `ContextBundle` preview.
- `never` entries remain excluded even if manually selected.
- Future progressions/knowledge remain hidden from earlier narrative scenes.
- Candidate AI outputs must not directly write Codex, progressions, or knowledge.

Acceptance:

- Scene mentions and Codex context preview are visible from Write.
- Effective-state rules still pass after frontend changes.
- No UI action silently mutates canon or story state from AI output.

### NS-409.7 Settings Recovery

Goal: finish the scoped model/settings product workflow.

Tasks:

- Complete model profile list/create/update/delete behavior.
- Complete service-key save/replace/delete/reuse behavior with clear status.
- Keep credentials out of files, logs, console, and Git.
- Keep cloud/provider policy explicit; no silent fallback from local to cloud.
- Preserve advanced provider details without crowding the main path.

Acceptance:

- Settings can manage the scoped model/provider workflow through real APIs.
- Tests cover save/replace/delete/test/list behavior where feasible without real secrets.

### NS-409.8 Review and Workshop Decision

Goal: stop placeholder pages from masquerading as product features.

Tasks:

- Decide whether Review and Workshop are in scope for this recovery pass.
- If in scope, define the minimum real workflows and APIs.
- If out of scope, replace shells with honest unavailable states and clear navigation behavior.
- Do not build large decorative empty surfaces.

Acceptance:

- Review and Workshop either work as scoped workflows or explicitly say they are unavailable.
- They do not consume layout space as fake dashboards.

### NS-409.9 Regression, Acceptance, and Handoff

Goal: close the recovery line only when product behavior and validation agree.

Tasks:

- Run command validation after each major package.
- Keep visual acceptance separate from command validation.
- Update the task and acceptance docs after each accepted package.
- Commit only coherent slices.

Required commands before claiming recovery completion:

```powershell
npm.cmd run test -w @novel-studio/web -- AppShell.test.tsx
npm.cmd run build
npm.cmd run test
git diff --check
```

Final acceptance requires user acceptance of the visual/product result.

## Non-Goals

- Do not implement AI auto-writing into prose, Codex, progressions, or knowledge.
- Do not replace archive/restore with hard delete without a product decision.
- Do not keep adding UI cards to fill empty space.
- Do not create new routine status files.
- Do not claim old M2/M3 completion prevents contract changes.

## Current Next Step

Start with `NS-409.1`: foundation audit for hierarchy and Codex API. Codex frontend work should not continue until the API/wrapper gap is explicit.
