## Objective

Deliver a real Research Note authority and author workflow that preserves exact
Source evidence, remains separate from story Canon, reports stale or missing
evidence, and can affect Codex only through a separately confirmed Proposal.

## In Scope

- Versioned Research Note JSON authority with stable identity, title, editable
  body, author metadata, explicit evidence references, status, timestamps, and
  revision protection.
- Exact evidence identity containing Research Database, Source, source content
  version, Chunk, original-language quote hash, and SourceLocation. A note never
  turns a generated summary into original evidence.
- Create, list, open, edit, archive, and restore commands with atomic writes,
  stale revision rejection, damage isolation, and deterministic diagnostics.
- Evidence resolution that distinguishes current, changed, missing, forbidden,
  and unreadable Source evidence without deleting or rewriting the note.
- A Research workspace note list/editor and a real `Add to project` action from
  an opened search result or passage. Original Source, parse state, permission,
  and note content remain visibly separate.
- A separate `Move to Codex` flow that requires an active Series, an explicit
  author-selected meaning, a concrete Codex target, and creation of a pending
  Series Proposal. It never writes Codex authority before Review acceptance.
- Proposal acceptance with target revision checks, an immutable snapshot, exact
  Research Note evidence, and stale-source blocking or explicit re-review.
- Focused contract, storage, server, Web, recovery, isolation, and connected
  browser verification.

## Out Of Scope

- Treating a Research Note as Canon merely because it exists or was generated
  by a model.
- Adding Research Notes to Workshop context selection or retrieval tools in this
  task; any such model access requires its own permission and budget design.
- Automatic summarization, automatic Canon promotion, or automatic Codex target
  selection.
- Source or Research Database archive/permanent-delete, source replacement or
  reparse, backup/restore, durable background jobs, operating-system locks,
  query translation, complete Embedding Settings, optical character recognition,
  or legacy binary `.doc` support.
- Changing the author's saved Provider credential, connection, or model profile.

## Logical Closure Boundary

| Boundary | Handling |
| --- | --- |
| Authoritative data | Versioned JSON Research Note files in the approved owner directory; Series-scoped Proposal and snapshot JSON remain the only pending Codex change authority |
| Read paths | Database note list/detail, evidence resolver, Review inbox, and Codex target preview |
| Write paths | Create/update/archive/restore Research Note; create/reject/edit/accept the separate Codex Proposal |
| Derived state | Notes are not stored only in SQLite or vectors; optional list projections must rebuild from JSON and are not required for this slice |
| User entry points | Research result/passage action, note list/editor, stale-evidence state, promotion form, and Review acceptance |
| Lifecycle | Notes support archive and restore; permanent delete is deferred because notes and Proposals may be audit evidence |
| Migration/rollback | New schema starts at version 1 with no existing authority migration; writes use same-directory atomic replacement and accepted Proposal application creates a rollback snapshot |
| Fixtures | Chinese-authored notes over Chinese, Japanese, and English Sources; changed/missing/forbidden evidence; damaged and duplicate note files; stale revisions; cross-database IDs; failed multi-file Proposal application |
| Acceptance | `docs/testing/NS-609_ACCEPTANCE.md` |

## Decisions

- Confirmed: a Research Note is not story fact by default. Its evidence remains
  anchored to unchanged original Source text, location, and hashes.
- Confirmed: `Move to Codex` creates a new Proposal and requires a second author
  decision in Review before Codex authority changes.
- Confirmed: no AI-generated summary can replace or masquerade as original
  Source evidence.
- Confirmed by the already-recorded database ownership rule and ADR-0024: each
  Research Note belongs to exactly one Research Database, can be managed with no
  Series open, and starts with at least one server-verified Source passage from
  that database. Series links never copy or own it.
- Confirmed by the already-recorded Codex distinction and ADR-0024: promotion
  requires an active Series. `world rule` targets Canon Description;
  `real-world reference` and `inspiration only` target Codex Research. The
  author may choose an existing Codex Entry or a named new Entry in an existing
  category.
- Confirmed: `aiPermission: never` still blocks model context but does not block
  local author note-taking or this Provider-free Proposal workflow.
- The named direct-to-React implementation checklist is
  `docs/design/ui-redesign/NS-609_RESEARCH_NOTES_UI_CHECKLIST.md`. It preserves
  the accepted Research workspace and applies these decisions without Figma.

## External Design References

- Zotero's current official note model distinguishes notes attached to one
  source item from standalone notes while keeping both as searchable library
  objects. This supports a Research Database owner plus explicit Source evidence
  references instead of making every note a novel-owned copy:
  https://www.zotero.org/support/notes
- Zotero collections are references to one library item rather than independent
  copies. The same library item can appear in several collections, which is the
  relevant mature analogue for reusing one Research Note across linked Series:
  https://www.zotero.org/support/quick_start_guide
- Novelcrafter keeps Codex description and Codex notes as separately versioned
  content. This supports retaining Novel Studio's existing distinction between
  Canon Description and non-Canon Research rather than flattening both into one
  promoted field:
  https://www.novelcrafter.com/help/docs/organization/revision-history
- Novelcrafter's Codex progressions are visible to artificial intelligence only
  from their story position onward and are not a substitute for plot-point
  instructions. This reinforces the need for an explicit author choice before a
  Research Note becomes a world rule or story-state change:
  https://www.novelcrafter.com/help/docs/codex/progressions-additions

These references informed interaction design. Novel Studio's controlling rules
are the author's already-recorded database ownership decision, the product
specifications, and ADR-0024 rather than the external products.

## Proposal Application Design Findings

The current `research-note`, `create-research-note`, `codex-create`, and
`codex-update` enum values are dormant scaffolding, not partially working
features. Source review found these exact runtime boundaries:

1. Proposal target availability currently opens every `codex-entry` target.
   That makes a `create-codex-entry` patch impossible because the preallocated
   target must not exist before acceptance.
2. Proposal preview and acceptance reject every patch whose target is not
   `scene-content`. Both normal acceptance and edited acceptance call the same
   Scene-only preparation and transaction writer.
3. A Codex Entry has two independent authorities: entry/Canon `revision` and
   Research `revision`. Existing-target promotion must use `codex-entry` with
   the entry revision for Canon Description, or `codex-research` with the
   Research revision for non-Canon material. One ambiguous baseline is unsafe.
4. New Codex creation currently generates its ID inside the direct create
   command. Proposal creation instead needs a preallocated target ID whose
   absence is checked at proposal creation, preview, and acceptance so Review
   and return navigation refer to the same target.
5. Proposal snapshots currently require a non-null target revision. A create
   patch has no prior target revision. The snapshot contract must represent a
   verified absent target explicitly rather than inventing a fake hash.
6. `research-note` exists as an Evidence source type but not as a Proposal
   source kind. Promotion needs an explicit Research Note source identity so
   availability and stale checks do not masquerade as a manual Proposal.

The application path must therefore be extended by target/action family, not by
loosening the Scene-only guard globally:

- Proposal creation validates exact action/target/field-path compatibility and
  captures Research Note revision plus every Source evidence identity.
- Existing Codex target preview rereads the exact entry or Research revision.
  New-target preview proves the preallocated ID and author-selected active
  category are still available.
- Acceptance rereads the originating Note and evidence before preparing any
  writes. Changed or missing evidence makes the Proposal stale; it never updates
  the Note automatically.
- The accepted new-entry transaction writes entry JSON, Codex Research JSON,
  Proposal snapshot, and decided Proposal JSON through one Series-root file
  transaction. Existing entry/research promotion writes the one target authority
  plus snapshot and Proposal in the same transaction.
- Research Note and Source files are read-only dependencies during acceptance.
  They remain under the Research Database root, so no transaction claims atomic
  writes across a Research Database and Series.
- Post-commit Codex indexing runs only after the file transaction succeeds. An
  index failure leaves committed JSON authority recoverable and marks derived
  projection work for retry; it cannot roll back by silently rewriting Canon.
- Batch preview uses the same target-family planner. Unsupported mixed-target
  behavior remains explicitly ineligible rather than falling through the Scene
  implementation.
