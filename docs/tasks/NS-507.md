# NS-507 Atomic Codex Tool Adapters

Status: complete
Created: 2026-07-10
Owner: Codex
Acceptance: `docs/testing/NS-507_ACCEPTANCE.md`

## Objective

Close M5.6B by making the existing limited Workshop Agent Codex create/update tools stale-safe and atomic. A confirmed execution must either commit every planned Codex, Progression, Workshop result, and terminal execution record together or leave all semantic authority unchanged.

The author-facing hierarchy remains `Series → Volume → Chapter → Act → Scene`; this task changes no hierarchy label or compatibility mapping.

## In Scope

- Serialize file transactions per Series so recovery cannot run against a live transaction.
- Add repository-owned atomic adapters for the existing `codex.create_entry` and `codex.update_entry` Workshop Agent tools.
- Commit created detail types, entry/research changes, Progression create/update/delete operations, the result message, and the successful tool execution record in one file transaction.
- Bind execution identity to both the server-owned tool request and the exact author confirmation payload.
- Capture entry, research, and targeted Progression revisions when the server creates an update tool request.
- Refuse execution when any captured revision is stale or missing.
- Bind Progression update/delete operations to the intended target entry or a relation involving that entry and to the captured effective Scene.
- Reject Agent attempts to move `effectiveFromSceneId`; a future dedicated move command is required for that behavior.
- Keep route-level failure recording after an atomic adapter refusal while ensuring no semantic Codex/Progression/result write survives.

## Out Of Scope

- Embedding-based detail schema planning and recommendation; NS-508 owns it.
- Durable multi-turn Agent runs and structured-output repair; NS-509 owns them.
- Legacy Workshop mode cleanup and module-wide route splits; NS-510 owns them.
- User-editable versioned Workshop prompts; NS-511 owns them.
- Durable Tool Plan/Grant records, dangerous-action classification, partial-result reporting, and Proposal fallback; NS-512 owns them.
- New Codex or Write tool kinds and UI redesign.

## Logical Closure Boundary

| Boundary | Handling |
| --- | --- |
| Authoritative data | Codex detail types, entries, entry research, Progressions, Workshop tool/result messages, and Workshop session metadata |
| Read paths | Server-owned tool-request creation, execute-route target resolution, repository Codex/Progression reads, and Workshop message reload |
| Write paths | Per-Series file transaction coordinator and repository-owned create/update tool adapters; execute routes may not compose authority writes directly |
| Derived state | Rebuild Codex index only after a successful atomic commit; no index rebuild on refusal/rollback |
| User entry points | Existing confirmed `codex.create_entry` and `codex.update_entry` execute endpoints |
| Lifecycle | Existing running/succeeded/failed tool execution states remain; archive/delete protections are regression-tested |
| Migration/rollback | No authority schema changes. Existing pending update tool requests without server-captured baselines are refused without mutation and must be regenerated; transaction rollback is tested with an injected mid-commit failure |
| Fixtures | Concurrent transactions, missing members, duplicate targets, stale entry/research/progression revisions, cross-entry Progressions, relation mismatch, Scene move, confirmation-payload mismatch, and mid-commit failure |
| Acceptance | `docs/testing/NS-507_ACCEPTANCE.md`; milestone rows M5-A33 and M5-A35 |

## Decisions And Open Questions

- The current limited execution claim remains a separate durable `running` write. All semantic effects and the terminal success/result record form the atomic commit. A failed adapter may then record a terminal failure without writing semantic effects.
- The confirmation hash covers the tool request and normalized confirmation payload. This is execution identity for the limited path, not a substitute for NS-512 Tool Plans/Grants.
- Progression update/delete may affect only a Progression owned by the target entry or by a relation whose endpoint includes that entry. Its captured effective Scene cannot change.
- No product question is open for this slice.
