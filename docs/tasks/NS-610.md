## Objective

Deliver a real, reference-aware lifecycle for isolated Research Databases and
Sources: archive, restore, explicit version-preserving replacement or reparse,
and exact-confirmed permanent deletion with honest blockers, recovery, and
connected UI.

The author explicitly corrected that Research Note was never requested.
Therefore NS-610 adds no Note mutation, deletion, promotion, or UI. It only
performs read-only compatibility checks where existing frozen NS-609 authority
could otherwise be corrupted by a Database or Source lifecycle command.

## In Scope

- Research Database version 2 compatibility, archive, restore, blocker report,
  deletion quarantine, exact-name permanent delete, and cleanup recovery.
- SourceDocument version 4 compatibility, active/archived lists, archive,
  restore, exact-name permanent delete, retained prior versions, file
  replacement, web-snapshot refresh, and current-original reparse.
- Active-only lexical/vector projection, multi-database retrieval, Workshop
  activation, and model-tool behavior after lifecycle changes.
- Classified bounded HTTP contracts and a connected Research UI with Active and
  Archived views, keyboard-reachable actions, dirty-state guards, blocker
  details, exact confirmation, progress/failure states, and responsive layout.
- Compatibility, migration artifact, rollback, injected failure, restart,
  isolation, redaction, and protected real-library safety evidence.

## Out Of Scope

- Automated backups or restore-from-backup drills.
- Durable cross-process locks, a general job queue, or background scheduling.
- Query translation, Embedding Settings UI, optical character recognition, or
  legacy binary `.doc` parsing.
- Model-triggered lifecycle writes. Research lifecycle remains author-only.
- New Research Note behavior or Research Note permanent deletion. NS-609 is
  frozen pending the author's explicit retain-or-remove decision; NS-610 only
  preserves compatibility with authority that already exists.
- Bulk edit, deduplication merge, Source identity splitting, or automatic web
  monitoring.

## Product And Technical Rules

- Database archive is blocked by any active or archived Workshop session that
  still records the database. It does not rewrite child lifecycle state.
- Archived databases and Sources remain locally readable but read-only and
  absent from all ordinary/model retrieval and new Workshop activation.
- Replacement preserves Source identity and author properties, creates a new
  immutable original/content version, and never overwrites a prior original.
- Reparse never accesses the network or changes original bytes. Web refresh is
  an explicit controlled replacement of the recorded URL.
- A pending Proposal that cites a Source or Research Database blocks permanent
  deletion. Unreadable possible-reference authority blocks conservatively.
  Existing Note quote snapshots survive Source deletion and report the Source
  as missing; NS-610 does not add a Note deletion command.
- Decided Proposals retain immutable evidence and remain historical after a Note
  or database is deleted; their source availability becomes unavailable rather
  than fabricated as current.
- Every permanent delete requires archived state, current revision, exact
  author-entered visible name/title, and a fresh server-side blocker check.
- Temporary failures retain selected rows and drafts. A successful delete moves
  selection predictably and clears only the deleted object's persisted key.

## Closure Boundary

- Contracts: lifecycle schemas, status queries, blocker reports, mutation
  inputs, versioned database/Source authority, and bounded public output.
- Storage: compatibility read, exact upgrade artifacts, version retention,
  atomic file deletion, database quarantine cleanup, external-reference scans,
  recovery, and derived-index reconciliation.
- Server: explicit routes and parse/acquisition reuse without path or secret
  disclosure.
- Web: database, Source, and Note lifecycle entry points and every loading,
  empty, blocked, conflict, damaged, success, and narrow-screen state.
- Existing consumers: Research search, multi-search, gateway, Workshop session
  activation, Proposal availability, and return navigation.
- Evidence: focused and adversarial tests, production builds, real browser,
  temporary-root disk inspection, full check, clean tracked state, and exact
  `data/library/` fingerprint.

## Completion Criteria

- Every acceptance row has actual evidence or remains explicitly manual.
- No archived or deleted database/Source can enter model context or search.
- No replacement overwrites an earlier original, and no Note quote is rewritten.
- Every destructive command reports actionable blockers and requires exact
  confirmation instead of relying on a client-only dialog.
- Product records do not imply backup, general jobs/locks, query translation,
  Embedding Settings, optical character recognition, or `.doc` support.
- Only task-scoped files are committed; temporary fixtures and `data/library/`
  are excluded and the latter remains byte-exact.
