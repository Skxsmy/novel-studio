# NS-608 Research-assisted Author Workflow Hardening

Status: todo
Milestone: M6.7
Predecessor: NS-607
Governing decision: `docs/adr/0021-tool-driven-research-retrieval.md`

## Goal

Validate and harden the completed Research-assisted Workshop path from an
author's perspective using saved real model credentials, realistic corpora,
multiple sessions, and multi-round conversations that continue until each
writing problem is actually resolved.

## In Scope

- Real saved-key calls through explicitly selected model profiles; credentials
  remain redacted and are never copied into fixtures, logs, or repository data.
- Several author scenarios such as historical fact checking, foreign-language
  source comparison, continuity research, terminology choice, and citation
  follow-up. Each session contains multiple model/tool turns until its stated
  author problem is complete before the next session begins.
- Authors provide ordinary requests rather than expert retrieval prompts. The
  system prompt, tool descriptions, continuation policy, and error feedback must
  sustain corrective behavior across later turns and sessions.
- Large-corpus import/index/search latency, context-budget pressure, cancellation,
  restart, damaged index rebuild, Provider failure, stale citations, permission
  changes, and database deactivation during later calls.
- Prompt-injection Sources, adversarial tool arguments, duplicate evidence,
  misleading cross-language false friends, and unsupported-model capability
  states.
- Final connected UI review and an explicit author acceptance decision.

## Out Of Scope

- Treating one or two short Mock Provider exchanges as real workflow proof.
- Expanding Research tools into automatic web browsing or authority writes.
- Storing or publishing the author's real credentials or private full corpus.

## Required Closure

1. Each scenario records the author goal, every retrieval call, evidence used or
   rejected, context budget, model response, correction, and final resolution.
2. Failures discovered in the real workflow are fixed and rerun end to end; a
   narrow regression test alone is insufficient closure.
3. Product records distinguish automated proof, diagnostic visual inspection,
   and the author's explicit visual/workflow acceptance.
4. Performance targets are measured on declared fixture sizes and hardware,
   with degraded behavior shown honestly when a target is not met.
5. The task receives its own acceptance record and exact test mapping before
   runtime edits begin.
