# NS-514 Reference UI Rebuild

Status: in_progress
Created: 2026-07-15
Owner: Codex
Acceptance: `docs/testing/NS-514_ACCEPTANCE.md`

## Objective

Rebuild the Novel Studio frontend from the tracked binding reference HTML in a
strict sequence: recover the pre-NS-514 runtime baseline, extract a complete
reference contract, reproduce the reference without legacy-UI additions,
obtain explicit author visual approval, audit reference controls against real
capabilities, and only then wire explicitly approved capabilities in place.

The detailed phase contract is
`docs/tasks/NS-514_REFERENCE_UI_REBUILD_PLAN.md`. The binding visual source is
`docs/design/ui-redesign/novel-studio-full-ui-redesign-reference.html`.

This task record is only an execution and evidence index for that existing
plan. It does not redefine, extend, or reinterpret the plan. P0 through P4 are
an exact reference reproduction, not a merge with the old UI. The P5/P6 audit
and in-place wiring described by the plan cannot introduce old UI structure;
they begin only after the P4 replica is explicitly accepted.

Canonical author-facing hierarchy: `Series → Volume → Chapter → Act → Scene`.

NS-514 does not imply that NS-511, NS-512, or NS-513 is complete. Their Prompt,
Tool Plan/Grant, Council, conflict/failure, and earlier visual-acceptance gates
remain open unless separately proved by their own acceptance records.

## In Scope

- P0: prove that tracked Web runtime files match the pre-NS-514 `HEAD`, remove
  only rejected untracked NS-514 runtime files if any exist, preserve all
  unrelated worktree changes, and prove the baseline Web build.
- P1: create docs/tasks/NS-514_REFERENCE_MANIFEST.md as the human-readable
  and machine-checkable inventory of tokens, regions, controls, states,
  interactions, media queries, and fixture-only content.
- P2: port the reference application frame, top appbar, workspace switcher,
  project/library menu, and New Series dialog without legacy shell additions.
- P3: port Overview, Settings, Plan, Write, Codex, Workshop, and the reference
  overlays in the order fixed by the rebuild plan.
- P4: assemble a reference-only replica, verify its declared structure and
  interactions, and stop for explicit author visual acceptance.
- P5: create
  docs/tasks/NS-514_REFERENCE_CONTROL_AND_CAPABILITY_AUDIT.md, covering each
  reference control and each real existing capability exactly once.
- P6: replace fixtures and connect controls only where the author-approved
  disposition preserves the reference node, structure, placement, and visual
  state while retaining existing safety and authority boundaries.
- P7: run focused and regression checks, record exact remaining gaps and
  deviations, and obtain final explicit author visual acceptance.

## Out Of Scope

- Treating the reproduction fixtures as production project data or successful
  backend operations.
- Adding legacy controls, substitute menus, routes, cards, banners, or panels
  that are absent from the reference during P1 through P4.
- Changing backend contracts, authority schemas, migrations, Provider
  behavior, or command safety merely to make the static reference work.
- Claiming that disabled Review or Research controls in the reproduction pass
  remove those product requirements or supersede their existing real APIs.
- Completing NS-511 versioned Workshop Prompt authority, NS-512 Tool
  Plan/Grant behavior, or NS-513 Council/final M5 gates by implication.
- Agent-owned visual acceptance or screenshot-loop approval.

## Logical Closure Boundary

| Boundary | Handling |
| --- | --- |
| Authoritative data | Unchanged through P4; fixture state is isolated and non-authoritative. P6 may read/write only through existing approved APIs and commands. |
| Read paths | P1 inventories the reference; P5 maps every real frontend/API read path before P6 integration. |
| Write paths | No product authority writes through P4. P6 preserves Proposal, Grant/confirmation, revision, snapshot, and repository-command boundaries. |
| Derived state | No schema change. Existing caches/indexes remain rebuildable and are not replaced by UI fixture state. |
| User entry points | Reference appbar, project menu/dialog, workspace switching, domain controls, and overlays; absent legacy entry points remain an explicit P5 decision. |
| Lifecycle | Existing archive/delete/recovery behavior is neither removed nor advertised through an unsupported reference control; P5 records every gap. |
| Migration/rollback | No authority migration. Source rollback is the pre-NS-514 `HEAD` Web baseline recorded at P0; phase commits must remain independently reviewable. |
| Fixtures | Reference fixture text/counts are allowed only in isolated reproduction fixtures/tests and must be removed or explicitly classified before production wiring. |
| Acceptance | `docs/testing/NS-514_ACCEPTANCE.md`; P4 and P7 each retain an explicit author visual gate. |

## Decisions And Open Questions

- On 2026-07-15 the author directed work to start on NS-514. The tracked
  reference HTML and the existing rebuild plan are therefore the binding
  structural source for P0 through P4.
- The original NS-514 rebuild plan owns the implementation direction. This
  execution record does not independently change product or UX specifications.
- Reference colors, typography, dimensions, spacing, and breakpoints override
  generic UI-skill recommendations. The skill guidance is retained only for
  semantic HTML, keyboard/focus behavior, honest disabled states, component
  ownership, and accessibility checks that do not alter the reference.
- Review and Research remain disabled exactly as shown during the reproduction
  pass. This is an approved staging state, not approval to remove existing
  product capabilities from the final connected UI.
- P4 acceptance authorizes the capability audit, not arbitrary integration.
  Every capability absent from the reference and every mapping that would
  change visible structure remains an explicit author decision at P5.
- "Wire approved controls in place" has the plan's narrow meaning: replace a
  fixture/local handler inside the same accepted reference control. It never
  authorizes combining the old and reference UIs or restoring an old control
  into the reference layout.
- No visible deviation from the reference is currently approved.
- The P3/P4 reproduction components consume the tracked binding HTML's exact
  DOM fragments, stylesheet, and local-only reference runtime at build time.
  This is a non-visible fidelity mechanism for the reproduction gate, not a
  production-data integration decision; P5/P6 must still classify and replace
  every fixture/local handler only after author approval.
- On 2026-07-15, after the P5 audit purpose and its separation from P6 wiring
  were restated, the author directed work to start. This records explicit P4
  visual acceptance and authorizes P5 audit creation only; it does not approve
  any control mapping, visible deviation, or backend integration.
- P5 is complete in
  `docs/tasks/NS-514_REFERENCE_CONTROL_AND_CAPABILITY_AUDIT.md`: all 368
  reference controls, 80 reachable old-UI API methods, 21 separately reviewed
  frontend-local capabilities, and seven excluded old fake/placeholder controls
  are accounted for. All 469 decision rows remain `pending_author`; P6 remains
  unauthorized until the author explicitly approves selected in-place mappings.
- On 2026-07-15 the author prohibited delete-and-readd replacement of an
  existing file. The durable rule is recorded in root `AGENTS.md`: existing
  paths must be updated in place, and oversized generated artifacts must be
  redesigned rather than temporarily removed.
- The author also prohibited using `apply_patch` to delete large files. For an
  explicitly authorized deletion, the path and size must be verified first;
  files at least 128 KiB use native `Remove-Item -LiteralPath` and are never
  deleted as part of a replace/rebuild sequence.
- Detailed P5 page comparisons requested by the author are recorded in:
  - `docs/tasks/NS-514_SETTINGS_UI_COMPARISON.md`
  - `docs/tasks/NS-514_WRITE_UI_COMPARISON.md`
  - `docs/tasks/NS-514_CODEX_UI_COMPARISON.md`
  - `docs/tasks/NS-514_WORKSHOP_UI_COMPARISON.md`
  These documents compare new-reference and pre-NS-514 functions in both
  directions and do not authorize P6 wiring.
- On 2026-07-15 the author approved P6 work for the Write surface only. The
  approved dispositions are: connect the complete existing NovelEditor and
  lightweight current-position Canon Description preview; redesign the full
  Story Change lifecycle in the accepted Write visual language with its add
  control at `right sidebar -> Scene page -> Story changes heading`; retain
  resizing and require delete confirmation; connect compact animated autosave
  with three automatic retries and no manual retry; add title context menus for
  rename/delete on Volume through Scene but not Series; keep every unsupported
  reference control visually present and disabled; and fix the disabled writing
  mode at Draft. No Settings, Codex, Workshop, or other P6 audit disposition is
  authorized by this decision.
- On 2026-07-15 the author explicitly rejected the first connected Story Change
  visual treatment and directed a complete UI redo. The rejection changes the
  presentation only: the approved Scene-page Add placement and the retained
  create/edit/collapse/resize/reorder/keyboard-move/focus/confirmed-delete
  lifecycle remain binding. The replacement is a Write-only presentation and
  still requires explicit author visual acceptance under A16.

## Completion Criteria

- P0 through P7 pass in order and every acceptance ID has actual evidence.
- The P4 and P7 author visual gates are explicitly recorded; neither may be
  inferred from diagnostics, screenshots, tests, or builds.
- Every reference control and pre-NS-514 capability has one audited disposition
  and all visible deviations have explicit author approval.
- Production pages contain real data or honest unavailable/disabled states,
  never reference fixture claims.
- Existing authority, safety, context, Proposal, permission, and lifecycle
  behavior is preserved for every connected control.
- Task-related changes are committed independently while unrelated user changes
  remain untouched.
