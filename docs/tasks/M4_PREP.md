# NS-400：M3 到 M4 的整备门

状态：进行中。  
位置：M3 完成之后、M4 模型连接之前。

## 目标

M3 已经建立真实的层级、规划、正文、设定库、故事进展和角色所知能力，但代码组织开始出现明显压力。M4 会引入 ProviderAdapter、上下文装配、提示词版本、调用日志和候选变更；如果直接叠加在当前结构上，项目会迅速不可读。

NS-400 的目标是把 M3 产物整理成 M4 可以安全承载 AI 能力的形态：

- 当前架构文档必须反映 M3 真实实现，而不是停留在 M0–M2。
- 过大的服务端、存储层和前端页面文件必须开始按领域拆分。
- M1–M3 的核心用户流必须有可重复测试，而不只依赖一次性浏览器记录。
- M4 的上下文、调用日志和 Proposal 契约必须先有边界，不允许在实现时临时拼接。

## 非目标

- 不实现真实模型调用。
- 不实现编辑团队、会审、候选稿应用或事实收件箱。
- 不改变现有文件格式语义；如需迁移，必须单独立项并先备份。
- 不为了追求行数指标做无语义拆分。拆分后必须更容易定位、测试和交接。

## 执行拆分顺序

1. **NS400-A：整备规格和验收基线**
   - 写入本任务文档、验收文档和任务索引。
   - 记录当前大文件规模和不可接受的增长方向。

2. **NS400-B：拆分服务端路由**
   - 从 `apps/server/src/app.ts` 先拆出边界清晰的领域路由。
   - 第一刀优先拆 `codex` 路由，因为它与 M4 上下文装配关系最近。
   - `buildApp` 继续只负责创建 Fastify、错误处理、注册领域路由和静态资源。

3. **NS400-C：拆分存储层领域模块**
   - 不一次性重写 `ProjectRepository`。
   - 先提取纯函数、路径/文件事务、Codex 查询辅助、层级投影等可测试模块。
   - 每次拆分必须保证公开行为、错误码和文件格式不变。

4. **NS400-D：拆分前端大视图**
   - 优先拆 `CodexView` 和 `WriteView` 的面板组件。
   - 状态提升保持谨慎，避免为了拆分引入跨组件隐式写入。

5. **NS400-E：建立可重复烟测 / E2E**
   - 已建立 `packages/storage/test/smoke.test.ts`，并提供根命令 `npm.cmd run test:smoke`。
   - 当前三条烟测覆盖：
     1. 创建系列 → 写中文正文 → 重启读取 → 删除 SQLite → 重建索引 → 搜索命中。
     2. 新建部 / 幕 / 章 → 移动场景 → 稳定 ID → 层级校验 `valid=true` → PlanningBoard 投影正确。
     3. 创建设定条目 → 正文提及索引 → `on-mention/manual/never` 资料范围预览 → 后文进展和角色所知不向前泄漏。
   - 这些测试不替代人工 UX 验收，但必须能在重构后自动报警。

6. **NS400-F：M4 契约先行**
   - 在实现模型前先定义最小：
     - `ContextBundle`
     - `ContextItem`
     - `PromptTemplate` 版本
     - `ModelCallLog`
     - `Proposal`
   - 明确服务端硬约束：AI 调用不得直接写正文、设定、摘要或角色状态。

## 不变量

- `npm.cmd run check` 必须持续通过。
- `main` 上不得留下半拆分状态。
- 文件格式、API 路径和错误语义保持兼容，除非任务文档明确要求迁移。
- 读取操作不得因为重构产生写入副作用。
- AI 相关占位不得假装可用；未实现功能仍要明确标记。

## 完成定义

NS-400 完成时必须满足：

- `npm.cmd run check` 通过。
- 至少完成服务端路由拆分、一个存储层拆分、一个前端视图拆分。
- 三条核心烟测可重复执行。
- M4 的 Context/Prompt/CallLog/Proposal 最小契约已经落文档或 contracts。
- `STATUS.md` 和 `HANDOFF.md` 指向 `NS-401`，且清楚说明还有哪些整理债务被刻意留到 M4 期间继续处理。
