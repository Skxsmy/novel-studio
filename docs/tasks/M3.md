# M3：规划、编辑器与故事事实

M3 把 M2 的“能保存场景”扩展成适合中文长篇的结构化写作工作台。任务按 `NS-301 → NS-302 → NS-303 → NS-304 → NS-305` 执行；后续任务只能依赖前项公开契约，不能绕过文件权威层直接写 SQLite。

## NS-301：作品层级与安全结构操作

状态：已实现，等待本任务完整验收记录通过后标记完成。

### 目标

建立 `Series → Book → Act → Chapter → Scene` 的显式、稳定、可迁移层级，使空幕/空章、排序、改名和场景移动都有唯一可审计含义。任何损坏引用必须被发现，不能因为“还能扫描到 Markdown”而静默丢弃。

### 非目标

- 不实现跨单本移动、删除/归档幕章、拖拽 UI、故事时间线或 AI。
- 不把 Act/Chapter 放入 SQLite 作为权威副本。
- 不以改名接口偷偷承担排序职责。

### 磁盘契约

```text
books/<bookId>/book.yaml                 # actIds
books/<bookId>/acts/<actId>.yaml         # bookId, order, chapterIds
books/<bookId>/chapters/<chapterId>.yaml # actId, order, sceneIds
books/<bookId>/manuscript/<actId>/<chapterId>/<sceneId>.md
```

所有实体使用永久 UUID。标题、顺序和物理路径改变时 UUID 不变。父清单决定成员关系与叙事顺序；子文件的父 ID 用于交叉校验。

### 强制不变量

对每个可正常打开的作品，必须同时满足：

1. `Series.bookIds`、`Book.actIds`、`Act.chapterIds`、`Chapter.sceneIds` 内部无重复。
2. 父清单中的每个 ID 都有且仅有一个对应文件；磁盘上的 Act、Chapter、Scene 文件也必须被且仅被一个父级引用。
3. `Act.bookId`、`Chapter.actId`、Scene 的 `bookId/actId/chapterId` 与父链完全一致。
4. 子实体 `order` 从 1 连续递增，并等于它在父清单中的位置。
5. Scene 物理路径与其父链一致；移动后旧路径不存在，新路径存在。
6. 同一 Scene ID 不能出现在两个章中，也不能在同一章中出现两次。
7. 结构损坏时，普通读取返回 `INVALID_DATA`；不存在的顶层查询目标返回 `NOT_FOUND`。不得 `continue`、过滤或自动修复。

只读校验器必须至少区分：`MISSING_*`、`ORPHAN_*`、`DUPLICATE_REFERENCE`、`MULTIPLE_PARENTS`、`ANCESTRY_MISMATCH`、`ORDER_MISMATCH`、`PATH_MISMATCH` 和无效场景文件。

### 命令语义

#### 创建 Act/Chapter/Scene

- 创建 Act：新 Act 与更新后的 `book.actIds` 一次提交。
- 创建 Chapter：新 Chapter 与更新后的 `act.chapterIds` 一次提交。
- 未指定位置创建 Scene：落入按 Book/Act/Chapter 顺序找到的第一个真实章；没有可用父级时明确失败，不生成悬空 UUID。
- 指定位置创建 Scene：验证完整父链后，将 Scene 和更新后的 `chapter.sceneIds` 一次提交。

#### 改名

`UpdateAct`、`UpdateChapter` 只接受标题。排序必须使用专用重排命令，避免单个实体的 `order` 与父清单发生分叉。

#### 重排

重排输入必须是当前子 ID 集合的完整、无重复排列：

- 少一个 ID：拒绝；
- 多一个未知 ID：拒绝；
- 重复 ID：拒绝；
- 仅顺序不同：更新全部子 `order` 与父清单，并作为一次文件事务提交。

失败后所有相关文件保持原状态。

#### 移动 Scene

输入只包含 `targetChapterId` 和可选的一基目标位置。目标 Act/Book 从目标章父链推导。

- 同章且无位置：幂等，无写入。
- 同章且有位置：等同完整重排，Scene ID 只出现一次。
- 跨章同单本：从源章移除、插入目标章、连续重算两章 Scene order、更新 Scene 父 ID、移动 Markdown 文件，一次事务提交。
- 跨幕：允许，但目标 Act 必须由目标章推导。
- 跨单本：NS-301 明确拒绝。
- 目标位置超过末尾：夹到末尾；小于 1 由输入校验拒绝。

### 文件事务与恢复

多文件结构命令采用 `.studio/transactions/<id>.json` 日志：

1. 在目标目录准备临时文件；
2. 记录目标、备份、是否原有文件及删除操作；
3. 标记 `committing` 后逐项替换；
4. 全部完成后标记 `committed` 并清理备份；
5. 下次访问作品时，未完成事务回滚，已完成事务只清理残留。

事务目标必须位于系列根目录，且同一事务不能重复写同一路径。

### M2 迁移

迁移服务于“Scene 已有 `bookId/actId/chapterId`，但 Act/Chapter 清单缺失或部分缺失”的旧作品。

1. 先复制 `books/` 到 `.studio/snapshots/pre-migration-<timestamp>/`。
2. 验证所有 Scene 的 Book 存在；否则停止并返回快照位置。
3. 以现有 Book 引用和 Scene frontmatter 合并推导 Act/Chapter；保留已有标题与创建时间。
4. 按 Scene 原 order 生成 `sceneIds`，并补齐连续 order。
5. 使用文件事务写入。
6. 运行正式层级校验；失败则报告问题和快照，不宣称迁移完成。

测试必须真的删除 Act/Chapter 清单；对已迁移项目执行 no-op 不能作为迁移证明。

## NS-302：真实规划视图

状态：已完成并通过验收，证据见 `docs/testing/NS-302_ACCEPTANCE.md`。

### 目标与边界

Grid、Outline、Matrix 和 Timeline 必须消费服务端返回的同一个 `PlanningBoard`，而不是各自扫描或重组一套权威数据。叙事顺序由 NS-301 父清单决定；故事时间来自显式 `TimelineEvent` 与独立事件顺序，禁止把 Scene 的单个日期字段冒充双时间线。

本任务实现本地规划、筛选、结构移动、显式故事事件和人工分叉决策。不实现 Codex 名称解析、自动语义分叉检测、主题实体管理或 AI；Matrix 在 Codex 完成前对 UUID 维度显示稳定短 ID，并诚实标注。

### 权威文件

```text
planning/timeline.yaml                  # eventIds，世界内事件顺序
planning/events/<eventId>.yaml          # 标题、时间标签、精度、关联 Scene、说明、标签
books/.../chapters/*.yaml               # Scene 叙事顺序
books/.../manuscript/.../<sceneId>.md   # 场景规划字段与正文
```

旧项目缺少 `planning/timeline.yaml` 时按空时间线读取；首次写入事件时创建。旧 `scene.storyTime` 仅作为兼容字段保留，不作为新时间线权威来源。

### PlanningBoard

查询结果必须包含：

- 按 Book→Act→Chapter→Scene 嵌套的层级投影；
- 按同一父清单展开的 `narrativeScenes`；
- 按 `timeline.eventIds` 展开的 `storyEvents`；
- 没有故事事件的 `unplacedSceneIds`；
- 从场景权威字段派生的 POV、人物、地点、情节线、标签和状态维度；
- 数据 revision，用于客户端判断刷新前后是否变化。

四种视图只允许对该结果做纯投影与过滤。切换视图不得写文件；选中的 Scene ID 与筛选条件在 Plan 工作区内共享。

### Scene 规划字段

在现有 `goal/summary/beats/pov/tags/*Ids` 基础上增加兼容默认值：

- `conflict`、`outcome`；
- `plannedCharacters`、`durationMinutes`；
- `planningState`：`aligned | review-needed | intentional-deviation | revise-prose`；
- `divergenceNote`。

显式用户编辑使用现有 Scene revision 冲突保护。规划字段和正文仍在同一个 Scene Markdown 中，不建立第二份规划副本。

### TimelineEvent

事件具有永久 UUID、标题、`timeKind`、人类可读 `timeLabel`、可选 ISO 时间、时间精度、持续分钟、关联 Scene IDs、说明与标签。世界内顺序只来自 `timeline.eventIds`；事件文件不维护第二个 order。

- 一个事件可以关联多个 Scene，用于并行叙述或同一世界事件的不同视角。
- 一个 Scene 可以关联多个事件，但 UI 首版明确展示多重关联。
- 创建、更新、删除、重排必须验证 Scene 引用和完整排列。
- 事件更新使用 revision；删除与重排使用文件事务。

### 视图行为

#### Grid

按 Book/Act/Chapter 分组展示 Scene 卡片。卡片显示标题、状态、摘要、POV、字数和可选规划字段。拖动卡片只调用 `reorderScenes` 或 `moveScene`；服务端返回后重新加载 PlanningBoard，不在客户端先修改权威数组。

#### Outline

线性展示 Book、Act、Chapter、Scene 与摘要。与 Grid 共用选中 Scene 和结构命令；折叠只是本地界面状态。

#### Matrix

列为叙事 Scene，行为所选维度值。支持 POV、人物、地点、情节线、标签和状态；单元格只由场景字段计算。筛选后 Grid/Outline/Timeline 同样只高亮或显示匹配 Scene，不维护第二套关联。

#### Timeline

并列展示：

- 叙事时间线：严格等于 `narrativeScenes`；
- 故事时间线：严格等于 `storyEvents`；
- 未放置区：没有任何事件关联的 Scene。

倒叙场景可以在叙事线靠后、关联事件在故事线靠前。未知或相对时间允许用标签和精度表达，不强迫现实日期。

### 计划与正文分叉

本任务不伪装自动理解正文。用户或后续分析器可把场景标为 `review-needed`，之后作者必须选择：

1. 更新规划字段并恢复 `aligned`；
2. 标为 `intentional-deviation`；
3. 保留规划并标为 `revise-prose`。

三种选择都是明确用户写入，不能由视图切换或后台读取触发。

- `DELETE /api/v1/series/:seriesId/timeline/events/:eventId`

## NS-303：Markdown 编辑器

### 目标

把 M2 的场景文本框升级为 Markdown 原生写作工作区，同时保证编辑器可替换、原稿可脱离应用阅读、外部编辑不会被静默覆盖。作者备注、候选文本、研究摘录和敏感资料不得混入正文；审阅意见必须锚定正文证据，并在正文变化后可靠重定位或明确报告失效。

### 范围

1. 使用 Milkdown/ProseMirror/Remark 编辑场景 Markdown；Milkdown 的内部文档状态只存在于运行时，不能写成权威副本。
2. 支持段落、标题、强调、粗体、列表、链接、引用和场景分隔线的 Markdown 往返；保存不得主动改写中文标点、空格或用户未触碰的文本。
3. 保留标题、字符数、段落数、保存状态和 revision 冲突保护；专注模式只显示标题、正文、保存状态和退出入口。
4. 浏览器本地保存崩溃恢复草稿。草稿记录 `seriesId`、`sceneId`、基础 revision、标题、正文和时间；恢复草稿不能绕过服务器 revision 检查。
5. 实现独立 Section 文件及列表、创建、编辑、归档和恢复。首版类型为作者备注、候选版本、研究资料、敏感资料、临时草稿。
6. Section 具有显式 AI 权限：`inherit`、`never`。`never` 永远不能进入任何 AI 上下文；正文是否进入 AI 仍由作者选择和调用权限决定。
7. 实现审阅锚点文件及创建、查询和重定位。锚点保存稳定 ID、目标场景、基础场景 revision、引用文本、前后文、初始字符位置和块 ID；不向正文注入私有标记。
8. 提供纯函数式上下文资格查询和锚点解析器，供 M4 上下文装配与 M5 审阅系统复用；NS-303 不调用任何模型。

本任务不实现 AI 候选稿、批注会话、Snippets、中文规则检查和 Scene Beats 状态机；它们分别由 NS-305 之后的编辑团队、后续写作增强任务处理。现有 `beats: string[]` 继续可显示，不在本任务改变场景文件版本。

### 文件契约

正文继续使用 M2/M3 的场景文件：

```text
books/<book-id>/manuscript/<act-id>/<chapter-id>/<scene-id>.md
```

Section 使用独立 Markdown 文件：

```text
sections/<scene-id>/<section-id>.md
```

文件由 YAML frontmatter 和 Markdown 正文组成。frontmatter 至少包含：

- `schemaVersion: 1`
- `id`、`sceneId`、`title`、`kind`
- `aiPolicy: inherit | never`
- `createdAt`、`updatedAt`、`archivedAt`

审阅锚点使用独立 YAML：

```text
review/anchors/<anchor-id>.yaml
```

锚点至少包含：

- `schemaVersion: 1`、`id`、`sceneId`、`blockId`
- `sceneRevision`、`exactQuote`、`prefix`、`suffix`
- `start`、`end`、`createdAt`、`updatedAt`

`blockId` 是锚点记录中稳定的逻辑块 ID，不要求写回正文。引用文本和上下文是重定位证据，不是允许模糊猜测的理由。

所有文件写入继续采用同目录临时文件、校验和与原子替换。归档 Section 只设置 `archivedAt`，不删除文件。SQLite 可以以后索引 Section 和锚点，但不得成为唯一副本。

### 锚点重定位规则

解析器按以下顺序工作：

1. 原字符范围仍精确匹配引用文本：状态为 `attached`。
2. 全文只有一个精确引用：移动到该范围，状态为 `relocated`。
3. 有多个精确引用：使用 `prefix`、`suffix` 和距离原位置的差值判定；只有一个最佳候选且证据无并列时才能重定位。
4. 引用已删除、候选并列或上下文不足：状态为 `orphaned`，不猜测、不自动改写锚点文件。

查询锚点时返回解析结果；只有用户后续明确确认重绑时才更新持久锚点。这样读取操作保持无副作用。

Section 更新和归档必须携带 `baseRevision`；过期 revision 返回 `409 CONFLICT`。创建锚点时服务端必须验证引用范围与当前正文一致；无效范围返回 `422 INVALID_DATA`。路径中的系列、场景和 Section/锚点归属必须交叉校验，禁止跨作品读取。

### UI 行为

- 中央编辑器直接编辑 Markdown 语义视图；场景切换时重建编辑器实例，不能把上一场景历史带入下一场景。
- 输入后显示“未保存”，自动保存时显示“保存中”，成功后显示“已保存”；冲突和错误必须持续可见，不能被下一次自动保存掩盖。
- 崩溃草稿与磁盘 revision 相同可提供一键恢复；基础 revision 已过期时显示“磁盘版本 / 恢复草稿”选择，不自动覆盖。
- 右侧抽屉提供“场景资料 / 附属文档 / 锚点”三个页签。附属文档编辑与正文保存相互独立。
- 用户在编辑器中选择文本后可建立锚点；空选择不可建立。锚点列表显示引用和 `attached / relocated / orphaned` 状态。
- 进入专注模式后左右抽屉、主导航和上下文工具隐藏，但必须保留退出专注模式按钮、保存状态和错误提示。

### 不变量

- **NS303-I01 文件权威**：场景和 Section 的 Markdown/YAML 是唯一可重建的权威数据，Milkdown JSON 与 localStorage 都不是。
- **NS303-I02 无静默覆盖**：正文与 Section 的过期基础 revision 一律拒绝。
- **NS303-I03 权限默认保守**：敏感资料默认 `never`；上下文资格函数面对未知策略或目标时拒绝包含。
- **NS303-I04 读取无副作用**：列出 Section、上下文资格和解析锚点不得写文件。
- **NS303-I05 锚点不猜测**：没有唯一证据时必须 `orphaned`。
- **NS303-I06 原稿纯净**：不得为了编辑器状态、锚点或评论向正文插入私有节点、隐藏 HTML 或应用 JSON。
- **NS303-I07 恢复受冲突保护**：崩溃草稿恢复后仍以其基础 revision 保存，不能覆盖外部修改。
- **NS303-I08 AI 零调用**：本任务任何操作均不得产生网络模型调用。

## NS-304：Codex

### 目标

建立系列级故事事实库，使人物、地点、物件、世界设定、组织、情节线和用户自定义类别都拥有可读、可迁移、可冲突保护的权威文件。正文中的名称出现可形成可重建提及索引，但提及不等于场景参与、设定成立或作者确认。界面称为“已确认设定”的 Description 属于故事事实；“参考笔记”必须保存为独立文档，不能混进同一 Markdown 正文后依赖 UI 隐藏。

### 范围与非目标

本任务实现：

1. 六个内置类别与可创建、改名、归档、恢复的自定义类别。
2. 设定库条目的名称、别名、标签、缩略图引用、补充字段、已确认设定、独立参考笔记、提及规则和模型可读范围。
3. Codex 条目的创建、读取、更新、归档和恢复；所有更新使用 revision 冲突保护。
4. 独立关系文件、方向、关系类型、描述、证据说明和可选场景有效区间。
5. 正文名称/别名提及索引、排除词、大小写策略、保守英文复数和同名歧义记录。
6. 删除 SQLite 后从场景、Codex 与关系权威文件重建索引。
7. 三栏设定库工作区及“已确认设定 / 参考笔记 / 识别规则 / 关系 / 正文提及”真实界面。
8. 规划追踪表使用设定库名称显示人物、地点和情节线，不再把 UUID 当名称。

本任务不实现进展记录、角色知识、伏笔状态机、模型调用、语义实体识别、昵称推断、指代消解或把参考笔记自动提升为已确认设定。它们分别属于 NS-305、M4 和 M5。自动提及只接受显式名称规则，不用模型猜测“她”“队长”等指代。

### 权威文件

```text
codex/
├─ characters/<entryId>.md
├─ locations/<entryId>.md
├─ objects/<entryId>.md
├─ lore/<entryId>.md
├─ organizations/<entryId>.md
├─ plot-threads/<entryId>.md
├─ categories/<categoryId>.yaml
├─ custom/<categoryId>/<entryId>.md
├─ entry-research/<entryId>.md
└─ relations/<relationId>.yaml
```

内置类别 ID 为 `character | location | object | lore | organization | plot-thread`，分别映射到固定目录。自定义类别使用 UUID，类别文件保存名称、图标、时间和归档状态；条目放在对应 `custom/<categoryId>/` 下。文件名 ID、frontmatter ID 和目录类别必须一致，否则数据无效。

条目是 YAML frontmatter + Markdown 已确认设定：

```yaml
schemaVersion: 1
id: <uuid>
categoryId: character
name: 林岚
aliases: [阿岚]
tags: [主角]
thumbnail: null
details:
  年龄: "28"
aiContextPolicy: on-mention
mention:
  caseSensitive: false
  matchAliases: true
  automaticPlural: false
  excludedTerms: [林岚港]
createdAt: <iso>
updatedAt: <iso>
archivedAt: null
```

Markdown 正文只能表示已确认设定。参考笔记使用 `entry-research/<entryId>.md`，其 frontmatter 至少包含 `schemaVersion`、`entryId`、`createdAt`、`updatedAt`。两个文档拥有独立 revision；更新已确认设定或元数据必须提供条目 `baseRevision`，更新参考笔记必须提供 `baseResearchRevision`。

关系文件至少包含：`id`、`sourceEntryId`、`targetEntryId`、`type`、`directed`、`description`、`evidence`、可选 `validFromSceneId/validToSceneId`、时间和归档状态。`directed: true` 时 A→B 不产生 B→A；`directed: false` 查询任一端都可看到同一关系文件，但不得复制成第二条权威边。关系状态变化在 NS-305 通过 Progression 表达，本任务不覆盖历史关系。

### 提及规则

1. 候选词只来自名称及启用后的别名；空白、重复和与排除词完全相同的候选词被移除。
2. `caseSensitive: false` 使用 Unicode 小写比较；保存的命中文本仍保留正文原样。
3. `automaticPlural` 只对 ASCII 英文单词生成保守的 `s/es/ies` 变体，不修改中文名称。
4. 每个条目的排除词先在场景中形成阻断范围。该条目的候选命中若落入阻断范围则被忽略；排除词不阻止其他条目正常匹配。
5. 同一起点优先最长候选，避免“林”吞掉“林岚”。同一范围若对应多个条目则写入歧义索引，不分配给任一条目。
6. 自动提及只写 SQLite 派生表，不改 Scene `characterIds/locationIds/plotThreadIds`，也不创建已确认设定或关系。
7. 归档条目不参加新提及索引；恢复后重建即可重新出现。

### 模型可读范围

- `always`：自动上下文中可包含。
- `on-mention`：当前场景存在文本提及或显式场景关联时可包含。
- `manual`：默认范围不包含，只有用户主动选择时可包含。
- `never`：默认范围和主动选择都不得包含。

资格判断必须由纯函数统一执行；未知策略默认拒绝。NS-304 只提供资料范围预览，不调用模型。后续来源权限和故事时间还可进一步收紧，不能放宽 `never`。

## NS-305：Progression 与角色知识

状态：已完成并通过验收，证据见 `docs/testing/NS-305_ACCEPTANCE.md`。

### 目标

建立故事事实随场景推进的历史层，使设定库条目、关系和角色知识不再只有“当前最终状态”。系统必须能回答：

- 到某个叙事场景为止，世界中已经成立了哪些事实；
- 某个角色在这个场景此刻知道、相信或误解什么；
- 某段关系在这个场景此刻怎样变化；
- 哪些未来变化被排除，并且不能泄露内容；
- 每条判断来自哪些正文、设定或关系证据。

Progression 按叙事场景位置计算有效状态；故事时间用于倒叙、插叙和矛盾提示，但不取代叙事可见性。世界真相和“角色此刻知道什么”必须是不同查询，不能用一个最终字段覆盖历史。

### 范围与非目标

本任务实现：

1. `codex/progressions/<progressionId>.yaml` 世界事实与关系变化记录。
2. `codex/knowledge/<knowledgeId>.yaml` 角色知识、相信和误解记录。
3. 记录创建、读取、更新、归档和恢复；所有更新使用 revision 冲突保护。
4. 按场景叙事位置查询条目此刻有效的世界事实、关系变化和角色知识。
5. Addition 与 Replacement 的有效状态计算：Replacement 不删除旧历史，只在查询结果中替换同目标同字段此前状态。
6. 证据引用验证：证据必须指向真实场景、设定条目或关系；若引用正文引文，引文必须能在对应场景正文中找到。
7. 未来信息隔离：早于生效场景的查询不得返回未来事实、未来知识正文或未来证据。
8. 设定库界面展示“进展记录”“角色所知”和当前场景有效状态。

本任务不实现：

- AI 自动抽取事实、自动更新设定或候选事实收件箱；这些属于 M5 Proposal。
- 自动语义矛盾检测、伏笔状态机或读者记忆评估。
- 指代消解、昵称推断或从提及自动生成事实。
- 故事时间自动改写叙事可见性；倒叙只作为需要人工判断的连续性线索。

### 权威文件

```text
codex/
├─ progressions/<progressionId>.yaml
└─ knowledge/<knowledgeId>.yaml
```

Progression 文件至少包含：

```yaml
schemaVersion: 1
id: <uuid>
target:
  kind: entry | relation
  entryId: <uuid|null>
  relationId: <uuid|null>
fieldKey: "description"
changeKind: addition | replacement
summary: "林岚从这一场起失去旧钥匙。"
effectiveFromSceneId: <uuid>
effectiveToSceneId: null
evidence:
  - sourceType: scene
    sourceId: <scene-id>
    quote: "旧钥匙落进了潮水。"
    note: "正文明确写出物件状态变化。"
createdAt: <iso>
updatedAt: <iso>
archivedAt: null
```

`target.kind = entry` 时必须提供 `entryId`，并且该条目存在；`target.kind = relation` 时必须提供 `relationId`，并且该关系存在。`fieldKey` 用于区分“整体描述”“外貌”“关系状态”“持有物”等被替换的状态槽；它是作者可读的稳定键，不参与自动解释。

CharacterKnowledge 文件至少包含：

```yaml
schemaVersion: 1
id: <uuid>
characterEntryId: <uuid>
subjectEntryId: <uuid|null>
relationId: <uuid|null>
stance: knows | believes | misunderstands
summary: "林岚误以为周野已经背叛。"
truthProgressionId: <uuid|null>
effectiveFromSceneId: <uuid>
effectiveToSceneId: null
evidence: [...]
createdAt: <iso>
updatedAt: <iso>
archivedAt: null
```

`characterEntryId` 必须指向人物类别条目。`subjectEntryId` 和 `relationId` 至少提供一个，用来表达“知道关于谁/什么”或“知道关于哪段关系”。`stance` 表示角色主观状态；`misunderstands` 可以与世界真相并存，不得被系统当作矛盾自动覆盖。

### 叙事位置与生效规则

1. 叙事顺序来自 NS-301 父清单展开的 `PlanningBoard.narrativeScenes`。
2. 若查询场景叙事序号为 N，记录 `effectiveFromSceneId` 的叙事序号必须小于等于 N 才可进入候选。
3. 若 `effectiveToSceneId` 存在，其叙事序号小于 N 时记录不再有效。
4. 同一 `target.kind + targetId + fieldKey` 的 Replacement 按生效序号和创建时间取最后一条；查询结果保留该 Replacement，以及它之后的 Addition。
5. Addition 永远不删除历史；它只在当前查询结果中累积显示。
6. 倒叙场景仍按读者看到它的叙事位置获得上下文；故事时间只用于后续连续性提示，不让 AI 提前知道后文事实。
7. 查询可以报告“未来记录数量”，但不得返回未来记录 ID、摘要、证据或关联目标的具体内容。

### 证据规则

证据支持三类来源：

- `scene`：正文场景。若提供 `quote`，服务端必须确认引文出现在当前场景正文中。
- `codex-entry`：设定库条目。用于说明该记录依据某个已确认设定。
- `relation`：设定库关系。用于说明关系变化依据已有基础关系。

证据必须至少提供 `sourceType`、`sourceId` 和 `note`。无效来源、跨系列来源或不存在的正文引文一律拒绝写入。读取有效状态时返回所有已纳入记录的证据；未来记录的证据不返回。

### API

- `GET|POST /api/v1/series/:seriesId/codex/progressions`
- `GET|PUT /api/v1/series/:seriesId/codex/progressions/:progressionId`
- `POST /api/v1/series/:seriesId/codex/progressions/:progressionId/archive`
- `POST /api/v1/series/:seriesId/codex/progressions/:progressionId/restore`
- `GET|POST /api/v1/series/:seriesId/codex/knowledge`
- `GET|PUT /api/v1/series/:seriesId/codex/knowledge/:knowledgeId`
- `POST /api/v1/series/:seriesId/codex/knowledge/:knowledgeId/archive`
- `POST /api/v1/series/:seriesId/codex/knowledge/:knowledgeId/restore`
- `GET /api/v1/series/:seriesId/codex/effective?sceneId=&entryId=&viewerEntryId=`

列表查询支持 `entryId`、`relationId`、`characterEntryId`、`subjectEntryId`、`includeArchived` 过滤。有效状态查询必须提供 `sceneId` 与 `entryId`；`viewerEntryId` 可选，提供后只返回该角色此刻的主观知识。

### UI 行为

- 设定库详情页新增“进展记录”和“角色所知”页签。
- “进展记录”显示所选条目或其相关关系的完整历史，并能新增一条从当前场景起生效的记录。
- “角色所知”允许选择知道者、涉及条目、立场、生效场景和证据说明。若当前条目是人物，默认把它作为知道者；否则默认把它作为涉及条目。
- 当前场景有效状态以“此刻有效”展示，并明确说明“未来变化已隐藏”。
- 界面用“世界事实”“角色所知”“误解”“生效场景”“证据”这类中文写作术语，不在主要界面暴露数据库式字段名。

### 不变量

- **NS305-I01 历史不覆盖**：新增或更新 Progression/Knowledge 不得改写 Codex 条目正文、关系文件或 Scene 正文。
- **NS305-I02 查询按叙事位置**：有效状态只由叙事位置决定；故事时间不提前释放未来事实。
- **NS305-I03 世界/所知分离**：世界事实、角色相信和角色误解分别返回，不互相覆盖。
- **NS305-I04 Replacement 只影响查询投影**：被替换的旧记录仍保留在完整历史中，可审计、可恢复。
- **NS305-I05 未来不泄露**：早期场景查询不得返回未来记录正文、证据或 ID。
- **NS305-I06 证据可追溯**：写入记录时必须验证证据来源存在；正文引文必须能定位。
- **NS305-I07 无静默覆盖**：Progression 与 Knowledge 的过期 revision 均拒绝写入。
- **NS305-I08 归档非删除**：归档记录不进入有效状态，但文件保留并可恢复。
