## Decision

M5 must make Proposal and Review reliable before Workshop becomes a broad chat workspace.

The implementation order is:

```text
protect current Write/Codex behavior
  -> define Proposal v2 and Review state machine
  -> implement Proposal storage/API and Review decisions
  -> implement Review UI on real Proposal data
  -> implement Workshop sessions/context/single-role call
  -> let Workshop messages create Proposals with exact Review deep links
  -> add authorized internal tool plans and command adapters
  -> add council, batch, conflict/failure, responsive, and visual acceptance coverage
```

Workshop is important, but it is not the first authority-changing surface. The durable value of Workshop output is the Proposal/Review loop. A chat panel that can produce cards but cannot reliably create, stale-check, apply, reject, or audit Proposals is not an accepted M5 result.

## Baseline

M5 starts after `NS-410` post-Slice 11 audit repair is command-verified and Project Recovery is accepted for the current stage by user decision on 2026-06-30.

That acceptance is the baseline for continuing into M5. It does not mean M5 Workshop, Proposal, Review, Tool Plan, or Council behavior is already implemented.

The following current behavior must not regress:

- Write does not return to repeated block cards or one textarea per stored block.
- Codex progression insertion remains behind the top Insert menu.
- Inline Codex progression components remain default-collapsed, expandable, draggable by release target, and UI-resizable.
- Write/Codex progression create/delete continues through scene-level atomic commands.

- Codex Canon and Detail editors remain bounded internal-scroll surfaces.

- Settings/AI provider paths must use explicit Provider selection and must not silently fall back to another Provider.
- No UI may expose audit IDs, hashes, prompt versions, or revisions in author-facing main paths unless the spec explicitly calls for a detail/audit view.

## Product Loop

The first accepted M5 loop is:

```text
Seeded or Workshop-created Proposal
  -> Review Inbox
  -> exact Proposal Detail route
  -> accept/reject/edit/stale decision
  -> command adapter applies or refuses the change
  -> source surface reflects the decision
```

Current Review boundary after the 2026-07-03 UI reset:

- Review is an author-facing decision workspace, not a Proposal management dashboard.
- The main route shows a pending-only queue and a focused before/after diff workspace.
- Accepted, rejected, edited, or stale Proposals leave the pending working queue.
- Evidence, source, reason, and audit-adjacent details remain reachable but default to a collapsed details area.
- Batch, impact, and diagnostic panels must not be reintroduced as permanent main-path columns. Batch behavior belongs to a later dedicated flow.
- Source-message return links remain available from the source/evidence details when the source is available.

Workshop enters the loop later:

```text
Workshop Session
  -> Message
  -> compact context selector backed by WorkshopContextBasket / Context Builder
  -> Model Call
  -> Proposal card
  -> exact Review Proposal Detail
  -> decision
  -> source message status updates
```

Current Workshop chat/settings boundary after the 2026-07-03 repair:

- Workshop conversations do not bind any scene by default; scene, chapter, act, full-novel, and Codex context must come from explicit context selections.
- General Chat is the default discussion mode and must not expose Proposal creation controls.
- General Chat system prompt content is fully visible/editable; there must be no hidden fallback prompt appended by the Workshop path.
- Workshop conversations are fixed as `chat` or `agent` when created; this is not a mutable per-message mode selector. General Chat remains discussion-only and sends only the visible author-editable system prompt. Agent sessions are dialogue-agent runs with a server-side structured-step protocol. Provider output is buffered, not streamed raw into the UI, then parsed into assistant text or server-owned `role: tool` request messages. The current limited Agent tools are `codex.create_entry` and `codex.update_entry`: structured JSON tool requests can create a Codex entry, update an existing entry's author-facing fields/research/details, and create/update/delete unified Codex Progression records only after author confirmation. Draft Details must match reusable detail types by stable detail type ID or exact normalized existing name; unmatched labels must never persist as free keys and instead require explicit confirmation to create the missing detail types before entry creation or update. Plain assistant prose, fake `Tool Call` text, and plain `Codex Draft` text are not executable tool protocol. Explicit author authorization inside the conversation is enough source basis for the Agent to draft and call the relevant tool; it must not refuse only because there is no external evidence. Category edits, relations, character knowledge writes, and broader Write/Codex mutations still require a dedicated Codex Proposal or future Tool Plan/Grant adapter.
- Mode, model setting, provider model override, system prompt, streaming, and reasoning-display controls live in a centralized settings dialog rather than scattered header/footer controls.
- Optional streaming may split model `<think>` or `<thinking>` spans and official provider-native reasoning fields into reasoning content. Reasoning must be visually distinct from answer text, visibly indicated when collapsed, and collapsible per message.
- Workshop chat messages must use a single broad reading column. User/author and assistant messages must not alternate as left/right narrow bubbles; role distinction is handled by compact metadata, restrained surface tint, and small accents while preserving the available conversation width.
- Author messages must appear in the conversation immediately after Send; Enter sends and Ctrl+Enter inserts a newline. A parsed attachment alone is enough to send a Workshop request; the UI must not require redundant composer text when the attachment is the request context.
- In-flight Workshop calls must expose a manual Stop control that aborts the current request/stream, preserves the author message and attachments, and reports a single stopped assistant state.
- Chat messages not linked to Proposal authority may be deleted. Messages linked to Proposal authority must remain protected.
- General Chat author messages may be edited and resent only inside `chat` sessions. Resend replaces the selected author message content, deletes later unprotected General Chat messages plus their bound attachments and branch records from the durable history, and then creates a new General Chat reply from the revised history. Agent sessions do not expose or accept edit/resend in this slice.
- Workshop session export is a session-level read action. Markdown export defaults to visible chat history without reasoning or prompt/context audit. The explicit include-reasoning option adds saved provider reasoning content, and the separate include-prompt-audit option adds model-call metadata plus reconstructed provider prompt/context records from durable ContextBundle links when available. The server export must emit UTF-8 portable Markdown, omit extracted attachment body text, must not render a Create Codex/Proposal action per message, and must not invent tool calls or hidden prompt/reasoning content.
- Embedding is a shared AI infrastructure layer for Agent schema planning, future Codex matching, Reference Library semantic search, context retrieval, and M6 vector index rebuilds. It uses `EmbeddingModelProfile` records separate from generation `ModelProfile`, routes by use case, supports profile-level batching/concurrency, and persists library-global embedding profiles under `.studio/embedding-profiles/`. The default recommendation is a local `BAAI/bge-small-zh-v1.5` HTTP service, but no model download, cloud fallback, vector index, or new author-facing Settings UI is completed in this M5 slice.
- In-flight streamed Workshop replies belong to the session that started the call. Switching to another session and back before the stream finishes must show the still-pending author/assistant messages and any received stream content instead of hiding the reply until completion.
- Workshop sessions need an explicit permanent delete entry in a compact session actions menu, separate from Archive. Permanent delete cascades unlinked session messages, message attachments, context baskets, and branch records; sessions containing Proposal-linked messages must be blocked with a reason instead of deleting audit-linked source material.
- Workshop follows `docs/design/ui-redesign/M5_WORKSHOP_UI_REDESIGN_REVIEW.html` for the current command-verified workbench-shell pass: the route uses the shared collapsible app project sidebar plus a dedicated full-height Workshop page body, Workshop topbar with New/More session actions, compact thread dock, active-session conversation header, broad left-accent message flow, message action menus, shorter composer, and a tabbed Story scope / Structure / Codex / Files context selector while using the existing real context-basket commands. Context, New/Add, More/session actions, message action menus, and Workshop settings floating surfaces close on outside pointer or Escape. This is a UI structure pass only; it does not add Tool Plans, new Agent write authority, or any fake controls. User visual acceptance remains pending.
- The app-level project sidebar's collapsed state follows the same redesign direction structurally while retaining the current light color system: project-initials brand block, icon plus short-label workspace buttons, and icon-only Switch Project/Settings footer actions. The expanded project sidebar is intentionally unchanged, and Workshop must not force a separate route-specific project-sidebar rail.
- Composer attachments are a Workshop user-message draft feature: `.txt`, `.md`, `.doc`, `.docx`, and text-extractable `.pdf` uploads parse immediately, send only parsed attachment IDs, and become `message-attachment` ContextBundle items on the next author message. The composer attachment icon must be a real button that opens the file picker and reflects disabled state during calls. Plain text and Markdown parsing must handle mainstream text encodings such as UTF-8, UTF-16, GB18030/GBK, Big5, Shift_JIS, and Windows-1252 instead of requiring the author to convert files manually. Attachments are not Reference Library SourceDocuments and do not enter retrieval indexes.
- Workshop calls must carry prior visible same-session messages as `workshop-chat-history` context, including extracted text from historical message-bound attachments. The current author message must be excluded from that history item because it is already the call `userRequest`.
- Workshop sessions use a neutral default title. A new empty session may be auto-named from the first author message or attachment file names after sending begins; once the author manually renames a session, automatic naming must not overwrite that title. Session titles are editable from the sessions list by double-clicking the title.
- Workshop Branch must copy the source session's visible message history through the selected source message into the new session, including message-bound attachment snapshots. The branch must not open as an empty chat, and copied messages must not inherit old Proposal links or old model-call/context audit IDs.

## Product Objects

M5 introduces or upgrades these objects.

### Workshop

- `WorkshopSession`: durable conversation container.
- `WorkshopBranch`: optional branch from a message.
- `WorkshopMessage`: author, role, system, tool, or result message.
- `WorkshopMessageAttachment`: server-parsed draft or message-bound file attachment used only as Workshop message context.
- `WorkshopContextBasket`: internal selected-context record for the session or current call. The UI must edit it through a compact context selector, not through a permanent right-side basket panel.
- `WorkshopContextItemRef`: pointer to scene, selection, Codex entry, section, research note, prompt/style context, or Review/Proposal source.
- `WorkshopToolDefinition`: internal project tool description, not an external model tool.
- `WorkshopToolPlan`: model- or user-created plan with ordered steps.
- `WorkshopToolStep`: one proposed internal command.
- `WorkshopToolGrant`: explicit user approval scope.
- `WorkshopToolCall`: audited execution attempt.
- `WorkshopToolResult`: completed, skipped, blocked, failed, or converted-to-proposal result.

### Proposal And Review

The existing `packages/contracts/src/proposals.ts` must be upgraded. Do not create a parallel Proposal model.

Required Proposal v2 concepts:

- `type`: `text-insertion`, `text-replacement`, `scene-summary`, `codex-create`, `codex-update`, `detail-type-update`, `relation-update`, `progression-create`, `planning-update`, `research-note`, `continuity-issue`, or equivalent narrowed enum.
- `source`: `workshop-message`, `write-selection`, `codex-entry`, `tool-plan`, `import`, `model-call`, or `manual`.
- `target`: target kind, target ID, author-readable label, base revision, optional field/block/range.
- `contextBundleId`: required for model-backed Proposals, nullable for manual/import/tool-generated Proposals when no bundle exists.
- `generator`: supports `ai`, `manual`, `tool`, and `import`; it must not require a model call for every Proposal.
- `riskLevel`: low, medium, high.
- `confidence`: optional numeric or enum confidence.
- `reason`: short author-facing rationale.
- `staleReason`: populated when target revision, reference, permission, or dependency invalidates the Proposal.
- `supersededBy`: replacement Proposal ID.
- `originalCandidate`: preserved when the user edits and accepts.
- `decision`: accepted/rejected/edited/stale/superseded/archive metadata with actor, timestamp, note, snapshot ID where relevant.
- `evidence`: scene/Codex/research/model-call/source-message references with revisions and quotes where applicable.

### Proposal State Machine

Persistent states:

```text
pending
accepted
rejected
edited
stale
superseded
archived
```

Allowed transitions:

```text
pending -> accepted
pending -> rejected
pending -> edited
pending -> stale
pending -> superseded
pending -> archived
stale -> superseded
stale -> archived
accepted -> archived
rejected -> archived
edited -> archived
superseded -> archived
```

`conflicted` is not a durable Proposal state in M5. It is an application or batch-preview result when a pending/stale Proposal cannot be applied because of current target state, lock, permission, missing reference, or command validation. If later implementation needs durable conflict records, that must be added by an explicit contract update.

## Storage Draft

All M5 authority files must be schema-versioned JSON and written with same-directory temp files, validation, and atomic replacement.

Recommended paths:

```text
workshop/
  sessions/<session-id>.json
  branches/<branch-id>.json
  messages/<message-id>.json

.studio/
  workshop/tool-plans/<plan-id>.json
  workshop/tool-grants/<grant-id>.json
  workshop/tool-calls/<call-id>.json
  inbox/proposals/<proposal-id>.json
  review/batches/<batch-id>.json
  snapshots/<snapshot-id>.json
```

Do not use a JSONL message log as the only durable Workshop message authority unless the implementation first proves atomic append, validation, crash recovery, and partial-line quarantine. The safer default is one JSON file per message plus rebuildable indexes for ordering/search.

SQLite remains rebuildable. It may index sessions, messages, proposals, status, target, source, and search text, but it must never be the only copy of Proposal/Workshop state.

## Command Adapter Boundary

Accepted Proposals and authorized Tool Plans must share the same command adapter layer.

Rules:

- AI may request a Proposal or Tool Plan, but it cannot execute authority writes.
- The server validates grant, target, base revision, references, permission, and risk.
- Tool adapters call existing domain/storage commands. They must not write authority files directly.
- Dangerous actions require explicit confirmation every time.
- A grant is scoped by series, session, tool plan, tool definition, target, risk, and expiration.
- New or changed plan steps require renewed approval.
- Partial failure must report completed, skipped, failed, and blocked steps.

Tool coverage is allowed only after Proposal/Review application is stable.
