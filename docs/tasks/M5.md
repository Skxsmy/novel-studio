## Decision

M5 must make Proposal and Review reliable before Workshop becomes a broad chat workspace.

The implementation order is:

```text
protect current Write/Codex behavior
  -> define Proposal v2 and Review state machine
  -> implement Proposal storage/API and Review decisions
  -> implement Review UI on real Proposal data
  -> implement Workshop sessions/context/single-role call
  -> let Workshop messages create Proposals with exact Review deep links
  -> add authorized internal tool plans and command adapters
  -> add council, batch, conflict/failure, responsive, and visual acceptance coverage
```

Workshop is important, but it is not the first authority-changing surface. The durable value of Workshop output is the Proposal/Review loop. A chat panel that can produce cards but cannot reliably create, stale-check, apply, reject, or audit Proposals is not an accepted M5 result.

## Baseline

M5 starts after `NS-410` post-Slice 11 audit repair is command-verified and Project Recovery is accepted for the current stage by user decision on 2026-06-30.

That acceptance is the baseline for continuing into M5. It does not mean M5 Workshop, Proposal, Review, Tool Plan, or Council behavior is already implemented.

The following current behavior must not regress:

- Write uses a continuous Tiptap-backed manuscript editor over `SceneBlockDocument`.
- Write does not return to repeated block cards or one textarea per stored block.
- Codex progression insertion remains behind the top Insert menu.
- Inline Codex progression components remain default-collapsed, expandable, draggable by release target, and UI-resizable.
- Write/Codex progression create/delete continues through scene-level atomic commands.
- Write and Codex autosave remains background work and must not disable active editing fields.
- Codex Canon and Detail editors remain bounded internal-scroll surfaces.
- Codex Details, Relations, Mentions, Progressions, category management, reusable detail types, and entry delete/archive/restore workflows remain intact.
- Settings/AI provider paths must not silently fall back across provider or local/cloud boundaries.
- No UI may expose audit IDs, hashes, prompt versions, or revisions in author-facing main paths unless the spec explicitly calls for a detail/audit view.

## Product Loop

The first accepted M5 loop is:

```text
Seeded or Workshop-created Proposal
  -> Review Inbox
  -> exact Proposal Detail route
  -> accept/reject/edit/stale decision
  -> command adapter applies or refuses the change
  -> source surface reflects the decision
```

Workshop enters the loop later:

```text
Workshop Session
  -> Message
  -> Context Basket / Context Preview
  -> Model Call
  -> Proposal card
  -> exact Review Proposal Detail
  -> decision
  -> source message status updates
```

Internal tool plans enter after the Proposal/Review loop is stable:

```text
Tool Plan
  -> explicit Grant
  -> validated command adapter
  -> authority write or Proposal fallback
  -> Review/source status
```

## Product Objects

M5 introduces or upgrades these objects.

### Workshop

- `WorkshopSession`: durable conversation container.
- `WorkshopBranch`: optional branch from a message.
- `WorkshopMessage`: author, role, system, tool, or result message.
- `WorkshopContextBasket`: selected context for the session or current call.
- `WorkshopContextItemRef`: pointer to scene, selection, Codex entry, section, research note, prompt/style context, or Review/Proposal source.
- `WorkshopToolDefinition`: internal project tool description, not an external model tool.
- `WorkshopToolPlan`: model- or user-created plan with ordered steps.
- `WorkshopToolStep`: one proposed internal command.
- `WorkshopToolGrant`: explicit user approval scope.
- `WorkshopToolCall`: audited execution attempt.
- `WorkshopToolResult`: completed, skipped, blocked, failed, or converted-to-proposal result.

### Proposal And Review

The existing `packages/contracts/src/proposals.ts` must be upgraded. Do not create a parallel Proposal model.

Required Proposal v2 concepts:

- `type`: `text-insertion`, `text-replacement`, `scene-summary`, `codex-create`, `codex-update`, `detail-type-update`, `relation-update`, `progression-create`, `planning-update`, `research-note`, `continuity-issue`, or equivalent narrowed enum.
- `source`: `workshop-message`, `write-selection`, `codex-entry`, `tool-plan`, `import`, `model-call`, or `manual`.
- `target`: target kind, target ID, author-readable label, base revision, optional field/block/range.
- `contextBundleId`: required for model-backed Proposals, nullable for manual/import/tool-generated Proposals when no bundle exists.
- `generator`: supports `ai`, `manual`, `tool`, and `import`; it must not require a model call for every Proposal.
- `riskLevel`: low, medium, high.
- `confidence`: optional numeric or enum confidence.
- `reason`: short author-facing rationale.
- `staleReason`: populated when target revision, reference, permission, or dependency invalidates the Proposal.
- `supersededBy`: replacement Proposal ID.
- `originalCandidate`: preserved when the user edits and accepts.
- `decision`: accepted/rejected/edited/stale/superseded/archive metadata with actor, timestamp, note, snapshot ID where relevant.
- `evidence`: scene/Codex/research/model-call/source-message references with revisions and quotes where applicable.

### Proposal State Machine

Persistent states:

```text
pending
accepted
rejected
edited
stale
superseded
archived
```

Allowed transitions:

```text
pending -> accepted
pending -> rejected
pending -> edited
pending -> stale
pending -> superseded
pending -> archived
stale -> superseded
stale -> archived
accepted -> archived
rejected -> archived
edited -> archived
superseded -> archived
```

`conflicted` is not a durable Proposal state in M5. It is an application or batch-preview result when a pending/stale Proposal cannot be applied because of current target state, lock, permission, missing reference, or command validation. If later implementation needs durable conflict records, that must be added by an explicit contract update.

## Storage Draft

All M5 authority files must be schema-versioned JSON and written with same-directory temp files, validation, and atomic replacement.

Recommended paths:

```text
workshop/
  sessions/<session-id>.json
  branches/<branch-id>.json
  messages/<message-id>.json

.studio/
  workshop/tool-plans/<plan-id>.json
  workshop/tool-grants/<grant-id>.json
  workshop/tool-calls/<call-id>.json
  inbox/proposals/<proposal-id>.json
  review/batches/<batch-id>.json
  snapshots/<snapshot-id>.json
```

Do not use a JSONL message log as the only durable Workshop message authority unless the implementation first proves atomic append, validation, crash recovery, and partial-line quarantine. The safer default is one JSON file per message plus rebuildable indexes for ordering/search.

SQLite remains rebuildable. It may index sessions, messages, proposals, status, target, source, and search text, but it must never be the only copy of Proposal/Workshop state.

## Command Adapter Boundary

Accepted Proposals and authorized Tool Plans must share the same command adapter layer.

Rules:

- AI may request a Proposal or Tool Plan, but it cannot execute authority writes.
- The server validates grant, target, base revision, references, permission, and risk.
- Tool adapters call existing domain/storage commands. They must not write authority files directly.
- Dangerous actions require explicit confirmation every time.
- A grant is scoped by series, session, tool plan, tool definition, target, risk, and expiration.
- New or changed plan steps require renewed approval.
- Partial failure must report completed, skipped, failed, and blocked steps.

Tool coverage is allowed only after Proposal/Review application is stable.

## Contract-Informed Figma

Figma remains mandatory before implementation, but Figma acceptance must be based on product objects and state transitions, not a static button inventory.

Required design basis:

- Proposal v2 object and state machine.
- Review decision loop.
- Workshop Session/Message/Context Basket objects.
- Tool Plan/Grant/Tool Call objects.
- Route and entry-point map.

Required user tasks in Figma:

1. Author opens Workshop and continues a session.
2. Author selects context and previews what the role can read.
3. Author receives a message that creates a Proposal card.
4. Author opens the exact Proposal detail from the card.
5. Author accepts, rejects, edits, or marks stale in Review.
6. Review links back to the source Workshop message.
7. A stale/conflict/failure/permission-denied state gives a recoverable next step.
8. Codex and Write tool actions are visually gated by Proposal or explicit Grant.

Buttons must exist only when their route, state, and backing behavior are defined or explicitly marked deferred.

## Completion Criteria

M5 is complete only when:

- Figma design for the implemented M5 scope is accepted by the user.
- Proposal v2 contracts and state machine are implemented and tested.
- Review can decide real Proposals before Workshop-generated Proposals are claimed.
- Workshop has persistent sessions, messages, context basket, context preview, and single-role calls.
- Workshop messages can create Proposal cards that deep-link to exact Review detail pages.
- Review decisions sync back to the source Workshop message.
- Authorized Tool Plans can execute approved Codex and Write commands through shared adapters, or safely convert to Proposals.
- Council first-round independence is tested.
- Batch accept, stale, conflict, failure, permission, and narrow states are tested.
- Existing Write/Codex/Settings/AI behavior remains covered and passing.
- `docs/testing/M5_ACCEPTANCE.md` records actual command results.
- `STATUS.md`, `TASKS.md`, `HANDOFF.md`, and related records are updated only with actual state, not projected plans.
