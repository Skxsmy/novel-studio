# NS-410 Block Write Editor and Unified Codex Progression

Status: in progress  
Started: 2026-06-26  
Owner: Codex

## Decision

This task is started by explicit user direction and overrides the previous recovery warning that said not to begin `NS-410`. The conflict is recorded here and in the project status files so the product decision is not trapped in chat history.

`NS-410` changes project authority from Markdown/YAML files to schema-versioned JSON files. Write manuscript authority becomes a structured JSON scene block document. Markdown remains a readable export/mirror/import boundary format; Word and full Markdown re-import remain later import/export work. This task also replaces the old YAML progression line with one unified JSON Codex Progression system for Canon description, reusable Details, world facts, and relationship changes so AI/context/preview can see only the values effective at the current scene and block position.

This is a storage authority change, not a license to break every frontend and backend interface at once. Existing HTTP contracts that are already used by the app should stay compatible where feasible while the storage layer converts between legacy DTOs and JSON authority files.

## Product Semantics

- Codex main entry pages maintain the initial/baseline state of the whole story.
- A Progression can target a Codex field, a world fact about an entry, or a relationship state.
- Write-sourced Progression occurs inside a scene and at a block position.
- A progression applies from that scene/block position forward through later blocks and later scenes.
- Earlier blocks/scenes cannot see later progression content, summaries, or IDs.
- Later progression records override or stack on earlier records per field.
- `add` prepends the new body to the currently effective field.
- `replace` sets the entire effective field to `body`; empty replace clears and hides that field.
- No independent `delete` operation exists in v1.
- Old `codex/progressions/*.yaml` files are retired. They are not a compatibility target and must not be read or written by the new runtime path.
- New Progression authority is `codex/progressions/<progressionId>.json`.
- AI and Proposal work may call the Progression API, but AI must still create candidate/proposal changes rather than directly mutating authoritative content.

## Scope

### In Scope

- Scene block document contracts and JSON persistence.
- Explicit migration or fixture regeneration for current Markdown/YAML test data.
- Deterministic Markdown-to-block import/migration where legacy Markdown support remains useful.
- Deterministic block-to-Markdown projection for search, mentions, word count, context body, and export endpoint.

- Scene/block-position aware Codex effective-entry API.
- Backward-compatible scene API behavior where possible: existing `content` reads return projected Markdown, and legacy `content` writes convert to blocks before JSON persistence.
- Context Builder uses projected Codex fields and hides empty fields.
- Write can load/save block documents and insert/edit/delete Codex progression blocks.
- Write progression panel lists scene progressions and stays synchronized with embedded blocks.
- Codex detail page exposes baseline/history/effective-at-scene views for the progressed fields.
- Markdown export endpoint for scene block document.
- Tests and docs for migration, rollback, future isolation, empty replace, conflict handling, damaged input, duplicate IDs, and deletion synchronization.

### Out of Scope

- Full Word export changes.
- Full Markdown or Word re-import into block documents.
- Rich typography/editor schema beyond the v1 block types.
- Direct AI writes to authoritative scene or Codex Progression files.
- Preserving old `codex/progressions/*.yaml` as a runtime authority path.
- A frontend-wide route/payload rewrite that is not required by the new storage authority.

## Data Model

`SceneDocument` gains:

- `document: SceneBlockDocument`
- `plainText: string`
- `content: string` remains as a Markdown projection for compatibility and export/mirror behavior.
- `revision` is computed from the authoritative scene file including the block document.

`SceneBlockDocument`:

- `schemaVersion: 1`
- `blocks: SceneBlock[]`

`SceneBlock` v1 kinds:

- `paragraph`: Markdown inline text.
- `heading`: heading level and Markdown inline text.
- `quote`: quoted Markdown inline text.
- `sceneBreak`: separator.
- `codexProgression`: embedded Progression component with `id`, `progressionId`, `createdAt`, and `updatedAt`.

Progression file path:

- `codex/progressions/<progressionId>.json`

Progression common fields:

- `schemaVersion: 1`
- `id`
- `kind`: `field`, `world`, or `relationship`
- `entryId`
- `field.kind`: `description` or `detail`, only for `kind: field`
- `field.detailTypeId`: required for detail fields
- `relationId`: required for relationship progressions
- `fieldKey`: author-readable state key for world/relationship progressions
- `operation`: `add` or `replace`
- `body`
- `summary`
- `effectiveFromSceneId`
- `source.kind`: `write-block`, `codex-page`, or `proposal`
- `source.sceneId`
- `source.blockId`
- `createdAt`
- `updatedAt`
- `archivedAt: null`

## Projection Rules

For `entryId`, target `sceneId`, and optional `blockId`:

1. Load baseline entry description and details.
2. Build narrative scene order from the existing hierarchy projection.
3. For the same scene, order blocks by the scene block document.
4. Include only Progression records whose position is before or at the target position.
5. Fold each field independently:
   - baseline is the initial value;
   - `replace` sets the current value to `body`;
   - `add` sets current value to `body + "\n\n" + current`;
   - empty replace yields an empty hidden field.
6. Return a projected entry shape close to `CodexEntryDocument`, plus `fieldStates` and hidden future count.
7. Hidden future count cannot expose future progression body, summary, or IDs.

## API Shape

- `GET /api/v1/series/:seriesId/scenes/:sceneId/document`
- `PUT /api/v1/series/:seriesId/scenes/:sceneId/document`
- `GET /api/v1/series/:seriesId/scenes/:sceneId/export/markdown`
- `GET /api/v1/series/:seriesId/codex/entries/:entryId/effective?sceneId=&blockId=`
- `GET /api/v1/series/:seriesId/codex/progressions?kind=&entryId=&relationId=&sceneId=&field=`
- `POST /api/v1/series/:seriesId/codex/progressions`
- `GET /api/v1/series/:seriesId/codex/progressions/:id`
- `PUT /api/v1/series/:seriesId/codex/progressions/:id`
- `DELETE /api/v1/series/:seriesId/codex/progressions/:id`

## Compatibility Strategy

- Public HTTP routes used by the current frontend remain stable unless a route cannot express the new behavior.
- `SceneDocument.content` remains available as projected Markdown for existing Write/editor callers, search previews, and export/mirror behavior.
- Existing scene update routes that accept Markdown `content` may remain as compatibility routes; the server converts Markdown to a block document and writes JSON authority.
- New block-aware code uses `/scenes/:sceneId/document` and the `SceneBlockDocument` DTO.
- Frontend migration is incremental: Write block editing, progression blocks, Codex field history, and context preview need new calls; unrelated Planning, Settings, model, and list surfaces should not be rewritten solely because storage authority changed.
- Backend changes should concentrate behind repository/storage methods and API route adapters so callers do not read or write `.json` paths directly.
- Tests must prove both new JSON document endpoints and retained legacy scene read/write behavior during the transition.

## Known Risks

- The current React UI is visually rejected; NS-410 must not claim final visual acceptance without user review.
- `packages/storage/src/index.ts` is large; touch only the necessary seams and prefer helper functions over further tangling.
- JSON authority removes the old hand-editable Markdown/YAML constraint. That is accepted because current data is test data, Markdown export remains readable, and schema-versioned JSON is easier to validate and migrate.
- API compatibility is a product requirement. Do not turn the storage rewrite into a full frontend/backend route rewrite unless the affected surface needs block/progression behavior.
- Full UI implementation may need additional design iteration after the backend/API vertical slice lands.
